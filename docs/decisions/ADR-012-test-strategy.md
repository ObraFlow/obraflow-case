# ADR-012 — Test strategy

**Status:** Accepted (2026-11-01)

**Project:** ObraFlow challenge

**Scope:** What is tested, at which layer, how the suites are run and what is deliberately not tested

**Related:** [ADR-001](ADR-001-postgresql-typeorm.md), [ADR-006](ADR-006-cumulative-approval-escalation.md), [ADR-007](ADR-007-purchase-order-approval-lifecycle.md), [ADR-008](ADR-008-monetary-precision-calculation.md)

## Context

The challenge calls tests desirable, not mandatory, and gives them no weight of their own. The risk in this system is not in how the screens look but in the rules behind them: sequential cumulative approval, exact money, immutable snapshots, version-checked publication and concurrent writes. A suite that is large but slow, flaky or about presentation costs more to maintain and to explain than it protects.

## Decision

1. **Business rules are tested at the API, against real PostgreSQL.** Row locks, `REPEATABLE READ` snapshots and constraints are the behavior under test, so no in-memory substitute is used (extends ADR-001). The API suite covers sequential approval, cumulative CoA publication and conflicts, rounding, authorization, membership and deactivation blockers, auditing, realtime hints and concurrency with deterministic barriers.
2. **Every run uses its own disposable database.** `scripts/test.mjs` creates an `obraflow_test_*` database, migrates and seeds it, runs the suites and drops it, even on failure. The runners and `database-guard.ts` refuse any database without that marker, so the development database is never touched.
3. **Pure front-end modules have a unit suite** that needs no browser, server or database: money and thresholds, order preview, list and audit query parsing, audit date ranges and notification storage.
4. **One acceptance journey runs the real stack through the UI.** A reviewer-style walk: sign in, provision users, a supplier and a project with a ladder, create orders from two members' sessions, approve and reject in order, and review the audit.
5. **A browser regression suite covers UI behavior that unit and API tests cannot:** failed, conflicting and uncertain writes and their recovery, URL and history behavior, drafts that must survive, loading, empty and error states, and automated WCAG A/AA scans (axe) of the critical screens. Where a failure must be induced, the specs stage the API response. Presentation details (colors, geometry and typography across many widths and themes) are not asserted; they were removed on the date of this ADR as costly and brittle.
6. **Two tiers.** `npm test` runs the quick tier (API, unit and the acceptance journey, about 90 seconds). `npm test -- all` adds the browser regression suite (about 9 more minutes). CI runs the quick tier only, so it stays fast and stable; the full suite is a local check before submitting.
7. **Tests take no screenshots.** Playwright keeps traces and screenshots on failure only. The README screenshots are generated by `scripts/screenshots.mjs`, a manual tool outside every test suite.

## Consequences

- At the date of this ADR the suites hold about 95 API tests, 47 unit tests, 1 acceptance journey and 226 browser cases, all passing locally. Local results do not verify a later commit; the CI result of the submitted commit does.
- Browser specs that stage responses can drift from the real API. The acceptance journey and the API suite are the check on that.
- Not covered by design: performance and load, visual regression, browsers other than Chromium, and real email, payment or identity providers (none exist).
- Support code lives in `apps/web/test/support`; specs are grouped like the app (`orders`, `projects`, `admin`, `audit`, `app`, `e2e`, `unit`).

## Alternatives considered

- **Run every browser test on every `npm test`.** Rejected: about ten minutes per run discourages running them, and the quick tier already protects the rules that matter.
- **In-memory or mocked database.** Rejected: it cannot exercise locking, isolation levels or constraints.
- **Visual regression or per-theme, per-width assertions.** Rejected: high maintenance for little protection of behavior.
