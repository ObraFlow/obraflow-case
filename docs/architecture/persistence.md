# Persistence boundaries

TypeORM is the primary persistence abstraction. All thirteen application tables have capability-owned `EntitySchema` mappings registered in `db/data-source.ts`. Physical schema changes remain migration-owned with `synchronize: false`; introducing these mappings requires no migration. Monetary NUMERIC values remain decimal strings, DATE remains date-only, timestamps map explicitly to ISO transport strings, and JSONB revisions retain complete immutable ladders. No eager relations, cascades or entity hooks perform hidden writes.

Routes validate HTTP inputs and apply method-specific auth guards; services own business rules, transaction boundaries and the visible sequence of named locking calls. Capability repositories receive the current `EntityManager` for reads, checks and writes, including bulk item/step/band inserts. They do not open independent transactions. Creation/decision helpers accept that manager so seed workflows retain their existing atomic composition. The entity inventory and transaction boundaries are described below.

All pessimistic row locks (`lockProject`, `lockUser`, `lockUsersForEligibility`, `lockSupplier`, `lockOrderForDecision`) live in `apps/api/src/db/locks.ts`, whose header documents the acquisition order per operation. Services call them in that order inside their own transactions; repositories no longer define locks. API errors likewise come from one module, `apps/api/src/lib/errors.ts`, which owns every error code and Portuguese message.

CoA publication locks the owning project, checks `expectedCoaVersion`, validates the complete ladder, then locks proposed users in UUID order and verifies active membership. Identical normalized content returns without writes. Changes replace active bands, increment the project version and append a complete revision in the same transaction. No application operation edits/deletes historical revisions.

Membership removal locks the project then target user with `FOR NO KEY UPDATE`. It blocks current CoA assignees and any undecided assignment on a pending project PO, including future steps. The pending check takes no PO lock, avoiding the reverse of decision locking; an in-flight undecided assignment conservatively blocks removal until its decision commits. Only the membership association is deleted. Existing creators, decisions, snapshots and revisions retain their user references. No migration or new historical store is needed; see ADR-005/009's 2026-10-23 extension.

User deactivation locks its target user before checking active-CoA and undecided-pending-PO blockers. It does not acquire project locks. Publication therefore either observes an inactive user and fails, or commits its assignment before deactivation rechecks and fails. Locking users in consistent UUID order prevents competing multi-user publications from reversing that order.

User creation completes Argon2 hashing before opening its write transaction; the user insert and lifecycle event still commit or roll back together. Missing seed identities follow the same pre-transaction hashing rule, after checking whether the identity already exists; reseeding never hashes or replaces existing credentials. Integration instrumentation observes the real hash completing before `START TRANSACTION` and forces a PostgreSQL lifecycle-insert failure to verify rollback of the user insert.

CoA reads use a service-owned `REPEATABLE READ` transaction so project existence/visibility, membership authorization, version and ladder belong to one snapshot. Membership listing also uses a small service-owned `REPEATABLE READ` transaction for its visibility predicate and returned rows. `visibleProject` requires the caller's explicit `EntityManager`; it never silently uses a global manager inside a transaction. ADMIN-only revision history keeps its explicit global-manager project-existence check: its visibility does not depend on membership, and the application has no project-deletion endpoint. PostgreSQL integration tests cover full-ladder failures, normalized no-op writes, stale versions, competing publications and publication/deactivation races. Locking, ordered band reads and append-only revision writes use TypeORM; locks retain their explicit PostgreSQL modes.

Deterministic query-runner barriers pause each protected read after its first project lookup establishes the snapshot, then commit membership removal and a new CoA publication before continuing. The in-flight read returns its original authorized snapshot, and a subsequent read by the removed member returns concealed `404`; ADMIN still reads globally. This guarantees a coherent request, not retroactive cancellation or immediate revocation of an already-running read. These reads take no write locks and do not change write isolation or lock ordering.

Project, user and supplier locks use `FOR NO KEY UPDATE`: these operations change no key, and the lock still serializes competing writes while allowing the `KEY SHARE` checks that PostgreSQL takes for foreign keys. This also permits compatible foreign-key checks by concurrent writers; a regression test exercises a direct membership insert while publication waits on a user. Application membership addition now locks project before user, matching removal and publication.

PO creation locks the project, resolves its ladder/version, locks the creator and selected approvers in UUID order, and locks the supplier before checking activity. Header, exact calculated items and immutable steps commit together. This shares the project lock with CoA publication and user/supplier locks with deactivation. Existing orders retain their revision FK and assignments.

Decisions lock the PO row, conceal unseen resources, check terminal/stale-step conflicts, and authorize current membership/assignment. The deciding user is locked and activity rechecked. One append-only decision is inserted; a final approval or rejection updates persisted status in the same transaction. Deactivation reads its blockers without locking POs/projects, so it cannot introduce the reverse PO/user lock order.

Full details use one SQL statement, including ordered items, steps and decisions, with NUMERIC columns explicitly cast to text inside JSONB (otherwise JSON decoding would yield JavaScript numbers). Current approval is derived from that snapshot. Creation/decision responses use the same query inside their transaction. Lists use database visibility, status/project/actionable filters and pagination within a consistent read transaction; they do not load full item/history detail.

The five direct domain-query calls are confined to three read projections: PO detail (`purchase-orders/order-detail.ts`, one ordered nested JSON query), PO list (`purchase-orders/order-list.ts`, count/page with lateral actionable-step selection), and audit (`audit/events-query.ts`, count/page over historical CTE/UNION sources). PO list and audit retain service-owned `REPEATABLE READ` transactions; ordinary writes retain default isolation. Raw rows describe runtime `Date` values separately from their ISO-string DTOs. Direct infrastructure SQL remains for health, migrations and seed-specific lifecycle/marker operations, not ordinary domain services.

Lock regression tests hold real rows until both HTTP workflows appear in PostgreSQL's blocking chain, then release and verify their results. They cover decisions, publication, deactivation, creation and membership removal. Captured TypeORM SQL additionally checks lock modes/targets, user UUID ordering, one transaction per write and all four repeatable-read paths (CoA, membership listing, PO list and audit).

The shared package exports compiled pure Zod transport contracts; root typecheck, build, API dev and test commands build it before consumption. It imports no browser, server or persistence modules. API typecheck also covers integration test sources.

Workflow seed configures only version-0 projects, never replaces an existing custom ladder, and composes each project's missing demo scenarios in one transaction with the same create/decide services. Visible immutable notes mark existing scenarios: reseeding does not reset a pending example that a reviewer has since approved/rejected. This seed-only lookup is not API deduplication. Missing/inactive demo prerequisites or a different saved ladder cause an explicit skip rather than reactivation or configuration overwrite.

## Project lifecycle (2026-10-30)

`ProjectLifecycle2026103000000` adds non-null `projects.is_active DEFAULT true`, preserving existing rows. Rename and archive/reactivate hold the same project `FOR NO KEY UPDATE` lock as PO creation, CoA publication and membership writes. Archive checks for `PENDING` orders after locking; creation checks activity after locking and verifying membership. Whichever operation commits first determines the competing request's `409`. Configuration writes check activity before any mutation, including no-op CoA publications or repeated membership removal. Decisions retain their existing PO/user lock order; the archive blocker read takes no PO lock and may conservatively reject while a final decision is uncommitted.

Lifecycle changes modify only project name/activity and now append the administration-audit history below. They do not delete records, create revisions/decisions, or rewrite history. Seeds skip archived workflows/membership additions and never reactivate archived projects. Real PostgreSQL tests force both PO-create/archive operations to wait, then verify both serial orders and the absence of pending orders in archived projects.

## Project administration history and supplier projection (2026-10-30)

`ProjectAudit2026103000001` adds `project_lifecycle_events` with noncascading project/actor foreign keys, constrained actions/actor kind, server timestamp and safe JSONB project/member snapshots. Project creation, rename, archive/reactivation and membership addition/removal append via the owning service transaction's `EntityManager`, after existing checks and under the existing project lock. Event insertion failure rolls back the mutation. No application update/delete path exists for these history rows. Repeated no-ops append nothing; distinct removal/readdition cycles remain separate records. Seed creation/additions/legacy-name upgrades explicitly record `SYSTEM` in their transactions and repeated seed preserves existing events.

The audit CTE combines this domain history with its original PO/decision/CoA/user sources and retained supplier creation/deactivation metadata, using the existing repeatable-read count/page snapshot. Supplier timestamps and actor IDs are projected directly, not copied into another table. Missing supplier actor metadata is `UNKNOWN`; known seed project operations are `SYSTEM`. Migration does not invent records for legacy project creators or previously removed memberships. Historical project/member details come from the event snapshot; the project context link can resolve the current retained project name. Supplier/user labels resolve from retained reference records. No new approval, monetary, authorization or workflow calculations are introduced.

Verification fingerprints now include all thirteen application tables (including `supplier_renames`, which holds one row per supplier rename for the audit trail). Test-only teardown deletes its own history before deleting fixture projects; production APIs retain history and offer no hard deletion. Lifecycle history remains application-level append-only data, not a database tamper-proof store.

## Schema changes and migrations

The schema belongs to hand-written SQL migrations in `apps/api/src/db/migrations/`, run by TypeORM's migration runner (`npm run db:migrate -w @dokimos/api`). The `EntitySchema` mappings only describe rows; they are not a source of schema.

- **Do not use `migration:generate`, `synchronize` or `migrationsRun`.** TypeORM cannot declare several things this schema depends on: the `DESC` ordering of the order indexes, the partial unique indexes on the CoA bands, the `CHECK` constraints, and the composite foreign keys that tie approvers to project membership and orders to a CoA revision. A generated diff would miss or try to "repair" them. `synchronize` and `migrationsRun` stay `false` in `db/data-source.ts`, and the API refuses to start while migrations are pending.
- **Applied migrations are immutable.** A schema change is always a new migration. Editing comments in an existing migration is harmless (TypeORM keeps no checksum), but changing its SQL would leave databases that already ran it different from fresh ones.
- **Name new migrations by hand, with a larger number.** TypeORM reads the last 13 digits of the class name as a timestamp and runs pending migrations in that order. The existing names use date-shaped numbers (`2026102100000`, `2026103000000`, `2026103000001`) that are larger than any real `Date.now()` value. A name produced by `migration:create` would therefore sort before the initial schema: existing databases would still run it, but a fresh database would try to run it before the tables exist and fail. Continue the pattern (`Name2026110100000`) and add the class to the `migrations` list in `db/data-source.ts`.
- **Keep the entities in step.** `apps/api/test/persistence.test.ts` compares every entity with the migrated database: columns, types, nullability, defaults, primary and foreign keys, unique and check constraint names, and indexes. It also fails if a table exists without an entity, and checks that the two order indexes remain `DESC`. A migration that adds a column, constraint, index or table without the matching entity change (or the reverse) fails `npm test -- api`.
