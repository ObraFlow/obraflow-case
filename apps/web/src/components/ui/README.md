# UI components

Locally owned components using the existing theme tokens, CSS Modules and Base UI behavior. Import each one from its source module. No remote registry service or extra dependency is required.

Layout and naming: hand-written components are PascalCase files beside their CSS Module. Files installed from a registry keep the name the registry gave them (`button.tsx` and `dialog.tsx` from shadcn, the `chevrons-*` animated icons from lucide-animated), so that re-installing updates them in place. Date controls live in `date/` and the registry icons in `icons/`.

Shared presentation remains in `@/components/`; resource-specific screens and components belong in `@/features/<feature>/`, with their CSS Modules. Purchase-order approval displays belong in `@/features/purchase-orders/`; live CoA configuration belongs in `@/features/coa/`. Keep domain API calls and workflow state out of shared UI primitives.

Keyboard focus uses a 3px accent outline drawn inside the control (`outline-offset: -3px`), strengthening the existing edge without changing dimensions or extending into a scroll container. Filled primary/save/approve/destructive buttons use their contrasting text color for this edge. Keep the indicator on the actual action, rather than also outlining its containing row/card. Compound text/date/money/search controls own the indicator on their wrapper while the inner input suppresses its own outline. Preserve visible outlines in forced colors; do not replace them with box shadows alone.

Form sections use the card surface. Ordinary input, selector, date and money-control interiors are transparent so they match their containing section or page. Keep the input border and disabled treatment visible. Floating menus, calendars and dialogs retain an opaque popover surface; do not make overlays transparent. On narrow screens, CoA exact thresholds have their own labeled rows beneath the proportional bar, keeping names and full monetary amounts independent of segment width.

View feedback lives in `@/components/Feedback`: `StateCard` provides icon/title/description/optional action; `ErrorState` preserves public API error text with optional read retry; `EmptyState` describes first-use or filtered results. Use compact presentation in member/search panels. Pages own action callbacks and pending state. Empty states are ordinary content; read failures announce an alert. Keep field validation and uncertain-write reconciliation specific to their workflow; these cards never retry a write or reload the window automatically.

Manual refresh actions use `@/components/RefreshButton`: disable while fetching, spin the icon (except under reduced motion), and show `Atualizando...` without changing button width. Icon-only controls retain their size and expose the busy label accessibly. `@/components/Loading` handles initial reads; refreshes retain mounted data until new results arrive, including on failure. Pages own request aggregation, cancellation and recovery. Refresh failures use a concise session-scoped notification; initial errors and write recovery remain inline.

`@/components/ToastProvider` owns authenticated session notifications. `useToast()` exposes `success`, `error`, `warning` and `info`, using green, red, amber and blue theme tokens respectively. Each method accepts `{ id, title, description?, action?: { label, onClick } }`. Success IDs notify once per session; repeated error/warning/info IDs update the same notification and may notify again after dismissal. `useRefreshFailure()` uses the error variant. Notifications survive route changes, clear on logout/persona changes and ignore late callbacks from old sessions; optional actions have the same session guard. The stack shows at most three notifications, with keyboard access and reduced-motion support. Keep field validation and uncertain-write recovery in their existing inline workflows.

Orders and audit share `@/components/Pagination`. An unavailable bookmarked page offers an explicit return to page 1; it never renders an impossible current/total range. Pages preserve filters/page size when returning and retain page size when clearing filters. Order view counts come from the same `GET /purchase-orders` response's `distribution` (`total`, `actionableByMe`, `byStatus`), scoped to actor visibility and the selected project, independent of status/actionable filters and pagination. List failure has one recovery action that refreshes page and distribution together; there are no separate count reads or count-only recovery. Narrow/coarse-pointer layouts enlarge shared actions and modal/calendar close controls. Mobile CoA approver controls use numbered rows with matching level colors, separate from the proportional bar and exact threshold rows.

## Modal composition

`DialogHeader` accepts an optional `identifier` string for the current resource, for example `<DialogHeader identifier={project.name}><DialogTitle>Gerenciar membros</DialogTitle></DialogHeader>`. It uses smaller, muted text at the top right, aligned with the bottom of the title when the header has enough width, and moves below the title on narrower surfaces. Its width is capped with an ellipsis and the complete text remains available in the `title` attribute. Keep it as context rather than a second dialog title. Reserve room for a top-right close button when the composition includes one.

Modals use a title row with an optional icon and a top-right close control, legible content, then a separated action footer where actions apply. Use `DialogHeader` and `DialogFooter` for new compositions. Closing is blocked while a write is pending. Projects, users and suppliers validate and submit directly in creation dialogs. Purchase orders use the dedicated `/purchase-orders/new` page with a separate item/total/approval review dialog before irreversible submission. CoA publication also reviews the expected and proposed versions, the full cumulative ladder and its effect on new orders; existing PO snapshots remain unchanged. Cancelling the review preserves the local draft. Validation, version conflicts and uncertain outcomes remain owned by the original page, with no automatic replay.

## Selectors

```tsx
const options = [
  { value: "joao", label: "João" },
  { value: "amanda", label: "Amanda", disabled: true },
];

<label htmlFor="approver">Aprovador</label>
<SingleSelect id="approver" options={options} value={approver} onValueChange={setApprover} />

<label htmlFor="people">Participantes</label>
```

Use unique string values and human-readable labels. An empty single value (`""`) represents no selection, or an explicit "Todos" option when included in `options`.

It supports `disabled`, `loading`, `readOnly`, `required`, `name`, `placeholder`, `emptyMessage` and the trigger's ARIA attributes. Associate a visible label through `id`, or provide `aria-label`. Associate page-owned validation through `aria-invalid` and `aria-describedby`; selectors never submit or fetch data. Loading prevents interaction. Read-only permits inspecting options while preventing changes, following Base UI semantics. Disabled options remain identifiable. Escape closes and restores focus; outside interaction dismisses the list. Portals avoid clipping in drawers, dialogs and scrolling containers.

## Calendar dates

For a range, use `<DateRangeSelector value={range} onValueChange={setRange} />` with `{from: "2026-10-01", to: "2026-10-29"}`. The optional `label` defaults to “Período”; `disabled` disables fields and actions. A single trigger summarizes the applied period and opens a Base UI popover with Brazilian date inputs, two adjacent months (stacked on mobile), range highlighting and Hoje/Últimos 7 dias/Últimos 30 dias presets. Presets only edit the local draft; Cancel/Escape/outside dismissal discard it. Calendar arrow keys, Home/End and PageUp/PageDown support keyboard selection. It keeps incomplete input local until **Aplicar período** (or Enter in a date input), rejects invalid/reversed dates, accepts the same start/end date, and supports either empty endpoint. **Limpar período** clears even an unfinished local draft. Values emitted are calendar dates with no timezone; the consuming page owns conversion to API timestamp boundaries and the inclusive/exclusive policy. Auditoria uses inclusive local days and an exclusive next-midnight API bound. Existing single-date behavior is unchanged.

```tsx
<label htmlFor="order-date">Data do pedido</label>
<DateSelector id="order-date" calendarLabel="Calendário da data do pedido"
  value={date} onValueChange={setDate} />
```

`value` uses `YYYY-MM-DD`, without a timestamp or timezone. Empty is `""`. The text field displays `dd/mm/aaaa`, accepts Brazilian or ISO entry, validates actual dates, and keeps incomplete/invalid text locally while emitting an empty value to prevent submitting a stale date. Invalid text is explained after blur. Server validation remains authoritative. Calendar arithmetic uses UTC only as an internal representation; dates never shift with a user's timezone.

The calendar supports arrows (day/week), Home/End (week boundaries), Page Up/Down (month), Enter/Space (select), and Escape (dismiss without changing the date). The text input allows direct entry of distant dates. `required` removes the calendar's clear action; `disabled`/`readOnly` prevent calendar editing. All controls retain the application's light/dark/system styles.

Add specific components when a real screen needs them. Keep validation, API calls, publication and recovery in the owning page; these are presentation components, not a form framework.

## Sections and dialog navigation

Use `Disclosure` for optional inline content inside an existing card or drawer. It uses the installed Base UI Collapsible, a full-width 44px trigger, neutral hover, visible keyboard focus and a neutral chevron that rotates when expanded. Sections open independently; there is no extra card outline or height animation. Chevron motion respects reduced-motion preferences. `title` and `children` are required; `open`/`onOpenChange` support page-owned state, with optional `defaultOpen`, `disabled` and root `className`. Panels stay mounted while hidden to preserve form inputs. Pages still own lazy fetching, errors and refresh state; history mounts its read contents only while expanded. Keep refresh and other actions inside the panel, outside the toggle.

Containers may set `--disclosure-trigger-max-width` and `--disclosure-margin-top` to adjust trigger width and space above the divider. The CoA card uses matching 24rem triggers and 1.5rem spacing; expanded panels retain the available card width.

`FormSection` adapts CMAPP's fieldset/legend component to the existing theme and CSS Modules. Use it for multiple meaningful input groups or member-list sections, not a one-field supplier/project form; validation, requests and drafts remain owned by the page.

Project/user/supplier creation dialogs use `?mode=create`; member management uses `?dialog=members`, deactivation uses `?deactivate=<id>`, and audit details use `?event=<source-qualified-id>`. Closing removes only the relevant UI parameter and retains other query parameters. Browser history and refresh restore the surface, not unsaved form contents. PO creation uses `/purchase-orders/new`; legacy PO `mode=create` links redirect there. Leaving that page discards unsaved fields, while its per-user submission marker survives navigation/reload and blocks another write until explicit reconciliation. Drafts and passwords are never serialized into URLs. Pending administrative writes keep their dialog open for same-route query navigation. Audit strips its UI-only event parameter before calling the existing API; unavailable records have a read-only fallback. Close controls replace redundant back/done navigation; inline removal cancellation and CoA discard confirmation remain explicit safeguards.

Creation dialogs keep a viewport-constrained fixed height and scroll their body internally. Form sections use explicit layout gaps rather than margins on fieldsets. `FieldFeedback` reserves two validation lines even when empty; long messages remain keyboard accessible within that space. DateSelector can opt into the same reservation using `reserveFeedback` and `feedbackMessage`. PO items use compact responsive rows with inline subtotals; no calculation or submission contract changes.

`MoneyInput` keeps its raw exact-decimal behavior by default for CoA confirmation. The PO unit-price field opts into `format="currency"`: it shows an R$ prefix/divider and a `0,00` placeholder. Typing `123` enters whole reais and displays `123,00`; pressing comma or period selects the fractional part for decimal entry. Grouping updates while typing, and blur pads unfinished cents. Brazilian formatted paste and canonical decimal paste are supported. Values passed to the caller remain exact decimal strings; excess fractional precision is preserved for validation rather than silently rounded. An untouched blank price remains required; explicitly entering zero is valid.

## Visual semantics

Use `Button` default for create/ordinary actions, `save` for persistence/publication, `approve` for approval and `destructive` for rejection/deactivation/removal. Outline/ghost actions remain neutral. `SaveConfirmation` requires `confirmLabel` and `pendingLabel`; intents are `save` (publication), `create`/`send` (when a separate review is warranted) and `approve`. Project/supplier/user forms submit directly after validation; PO review opens a separate dialog over the dedicated creation page. Required-field errors appear on attempted submission and focus the first invalid control; external prerequisites and pending/uncertain states still disable writes. These variants only select styling; the page still owns validation, confirmation, pending guards and recovery. Disabled controls use explicit surface/text/border tokens, with no opacity on historical records.

Typography and both themes live in `src/styles.css`, including rem role tokens and Tailwind aliases. `AlertCard` distinguishes information, attention and failure with a decorative icon plus text. Use `info` for guidance and normal status, `warning` for missing prerequisites, conflicts or uncertain outcomes, and `error` for failures. Every error message uses `AlertCard variant="error"`; the old `.error-box` style is gone. Choose between a toast and a card with the rules in [Feedback surfaces](../../../../../docs/architecture/frontend.md#feedback-surfaces). Preserve existing alert/status semantics and field descriptions. Do not use rejected/pending workflow tokens for general errors/warnings. Long field feedback remains scrollable inside its reserved height. See [visual conventions and token ownership](../../../../../docs/brand/README.md).
